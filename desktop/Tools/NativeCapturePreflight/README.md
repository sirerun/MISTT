# Native paired-capture preflight

This isolated macOS 14.2+ prototype qualifies native ownership of a microphone and one explicitly selected TikTok LIVE Studio audio process. Its SwiftPM tools version is 5.9. It is a preflight harness, not the product capture engine.

Opening the app only inventories Core Audio process objects and shows bundle IDs, PIDs, HAL IDs, and output-running state. It never selects a fallback target. Pressing **Start paired capture** requests microphone permission and starts an inclusion-only `CATapDescription` for the exact `com.tiktok.livestudio.desktop` process object, in a private aggregate with `muteBehavior = unmuted`; the same action starts microphone input. A missing or ambiguous target fails closed. If an audio-producing helper has been explicitly identified, pass each validated helper bundle ID as a separate `--include-helper-bundle-id <bundle-id>` app argument; every configured identity must resolve to exactly one live HAL process object. No public LIVE is needed: use only local help/tutorial/preview playback. Callback meters report bounded sampled energy and timing; no raw audio or transcripts are written to disk.

Both callbacks share one epoch and start/stop host-time cutoffs. All anchors and cutoffs pass through `AudioConvertHostTimeToNanos`; `_ns` values are never raw host ticks. Each callback examines at most 32 evenly spaced sample positions per channel and sends only a quantized RMS scalar plus its time interval through a fixed 256-entry per-source SPSC ring. No PCM block is queued or written to disk. Queue overflow is visible. A bounded meter supports checking that selected-app output reaches the tap and that unrelated playback does not; those physical checks remain pending. The 16 kHz mono s16le converter remains a deterministic fixture seam. Cutoff accounting replays the latest in-flight metadata record after callbacks quiesce; sample-level PCM cutoff correctness still requires production integration. A stop during in-flight HAL startup closes the gate and has a one-second fail-closed process watchdog; it does not claim successful closure. The selected app process is polled once per second; inventory read errors or selected process disappearance mute both sources.

The UI does not start capture on launch. Do not click **Start paired capture** until the coordinator is ready to observe the separate microphone and system-audio permission prompts. Grant or deny decisions are owned by the coordinator. Do not reset TCC globally. If a permission was already denied, use the normal per-app macOS privacy controls with the coordinator present to arrange any retest.

XCTest launches the fixed `/bin/cat` executable without a shell to qualify an owned helper pipe’s heartbeat, EOF, and monotonic timeout behavior. This verifies the watchdog signal path only; it does not establish a live capture teardown or Go bridge integration.

`Scripts/build-app.sh` creates an ad-hoc signed `.app` at `/Volumes/BuildOffload/artifacts/mistt-native-preflight/MISTT-Capture-Preflight.app`; it fails if that artifact already exists. To test a specific development identity, set `MISTT_DEV_SIGN_IDENTITY` explicitly at invocation. The bundle uses the proposed production identifier `com.sirerun.mistt`, `NSMicrophoneUsageDescription`, `NSAudioCaptureUsageDescription`, and the hardened-runtime microphone entitlement. This app’s TCC grants do not establish permission continuity across a future Developer ID signature; final signing and TCC attribution remain a later release/installation gate.

The app inventories target/helper candidates but requires exactly one live process object per configured bundle ID; output-running state remains diagnostic so silence does not trigger fallback. Helpers with other identities are displayed but not auto-included. Actual TikTok process/helper identity, both TCC grants/denials/revocations, positive target-signal and unrelated-process exclusion, audible playback after stop, sample-level exact cutoff behavior, and cleanup under relay/IPC loss remain physical-host gates. Signal/exclusion acceptance needs headphones to rule out microphone room pickup; the `call_audio` route label identifies the selected process path, not a speaker. XCTest verifies watchdog behavior against an owned helper pipe, conversion, fractional/end-exclusive cutoff, a deterministic callback/stop interleave, bounded scalar queue overflow, exact-target rejection, and native-format-to-16 kHz mono s16le fixtures including the current 32 kHz stereo microphone format. These tests do not prove live tap audio or sample-level cutoff correctness.
